## Первоначальная проверка

Аудит выполнен read-only по состоянию исходного кода до исправлений, обсуждённых с root 2026-09-05. Файлы root не изменялись этим агентом. Root сообщил, что исправляет session selection, residual initialization и повторно строит KASE archive по всем календарным дням; приведённые ниже номера относятся к проверенному снимку, а не к ещё не завершённому финальному запуску.

## Конкретные находки

1. **KASE placeholder может вытеснить полную торговую сессию.** `liquidity/experiment.py`, `build_panel`, сортировка `num_sess` и `drop_duplicates(keep='last')` выбирала максимальный номер, после чего `active` требовал positive deals. Для USDKZT_TOM 2020-03-31 session3 имеет volume72.15m и deals0, а session2 — тот же volume, deals272 и валидный диапазон. Для 2020-08-21 аналогично volume116.336m, session3 deals0 против session2 deals439. Реальные дни выбывали из расчёта доходностей и rolling liquidity. Дополнительно 2020-07-28 session3 содержит 96,788,000/421 против session2 96,789,000/422: последнее значение не всегда кумулятивный superset. Исправление предложено: приоритет полной валидной записи, затем latest среди одинаково полных; конфликты сохранить, volume не суммировать. Root принял.

2. **Замороженные параметры ещё не означают точного исходного prediction function.** `kazakhstan/experiment.py`, первоначальный `Adapted.fit`, использовал `GradientBoostingClassifier(init=FrozenEstimator(pooled.classifier))`. Идентичность estimator object и отсутствие изменения pooled predictions подтверждены. Но sklearn GBC внутри `_raw_predict_init` преобразует признаки в float32; исходный HGB получает float64. В 24m/2023 затронуты 5/242 test rows: max initial-probability shift .0379145, initial-logit shift .337916, resulting raw prediction shift .024258. В 120m/2026 — 1/156, initial-probability shift .0162509. Остальные шесть annual configurations совпадают. Изменение raw Brier мало, но математическое утверждение «исходная функция +40 деревьев» было неточным. `output/root_frozen_init_audit.json` содержит расчёты. Root принял и заменяет на явное residual boosting поверх исходного float64 logit; новые результаты требуют повторной проверки.

3. **Metadata context checkpoint не связывает фактические внешние входы.** `kazakhstan/experiment.py`, `evaluate`, параметр `panel` позволяет передать augmented Halyk/KASE panel, но receipt всё равно задаёт `source_panel` и `source_sha256` от default frozen V3 pickle. Это не hash actual context panel. Нужен content hash переданного panel и hashes использованных source/feature receipts, иначе изменение внешних данных не отражается в описании provenance checkpoint. Findings передан root, исходный код агентом не менялся.

4. **Импорт run_context запускает обучение и перезапись.** `kazakhstan/run_context.py` содержит основной цикл на верхнем уровне модуля. Импорт автоматически вызывает 16 `evaluate` (64 annual fits) и записывает outputs. Рекомендуется `main()` + `if __name__ == '__main__'`. Это не ошибка уже исполненного CLI эксперимента, но нарушает безопасное использование как импортируемого benchmark API.

5. **Timing receipt смешивает часы.** Для KASE/Halyk lag2 означает +2 calendar days; для MOEX код добавляет один CBR effective row к уже существующему V3 lag1. При длинных выходных это больше одного календарного дня. При этом исходный CNY basis остаётся baseline lag1. В коде это объяснено, но receipt `lag_calendar_days:2` и общий model suffix недостаточны: нужны per-source timing fields. Это metadata/interpretation finding, не обнаруженный lookahead.

## Подтверждённые свойства

- Liquidity panels имеют уникальные date×corridor keys; в добавленных модельных признаках нет ±Inf. As-of joins направлены назад, `available_date<=decision_date`, lag assertions выполняются. Same-date gate присутствует для Halyk personal/legal и Halyk/KASE market gaps.
- На Liquidity augmented panel запуск **без новых признаков** воспроизвёл старые pooled baselines: 4415 строк для каждого train-window, target и candidate flags совпадают, maximum calibrated-probability difference <=1.12e-16. Таким образом сами join/row order не меняют baseline или eligible OOT sample.
- Halyk-side интерпретация правильная: BANK SELLS RUB; log(RUB sell KZT/RUB)+log(official RUB/KZT) имеет правильную ориентацию. Это обратная сторона относительно продажи рублей отправителем, поэтому объявлять её all-in RUB→KZT execution нельзя. Код и loader этого не делают. Conflicting bank-date rows исключаются до join, timestamp преобразуется через историческую зону Asia/Almaty.
- `temporal_split` использует только прошлый train и prior-year validation, с horizon purge по коридорам. KZT stage2 использует только KZT train, full pooled training допустимо. `Ready` closure синхронно подаёт уже обученную модель в `core.run_fold`; нового fit на validation/test не происходит. OOT labels не участвуют в выборе residual weight, Platt или thresholds.
- По обеим train-window стратегия `kzt_pooled` имеет **точно те же raw probabilities** и candidate flags, что V3 на 883 KZT строках. Calibrated probabilities различаются (max .172239 для24m, .136086 для120m), потому что Platt теперь обучается только на KZT validation вместо pooled пяти коридоров. Root подтвердил, что это намеренный calibration-only adaptation control. Поэтому incremental residual improvement следует сравнивать с `kzt_pooled` same-window; отличие от старой V3 модели отдельно раскладывать на local calibration и residual steps.
- Повторное использование prior-year validation для фиксированной shrink grid, Platt и cadence не раскрывает OOT labels, но добавляет возможность переобучения на validation. Все выбранные по результатам направления остаются retrospective exploratory. Объём KASE — объём торгов, а не банковский spread или order imbalance.

Окончательные hashes/числа KASE не фиксировались: root расширяет архив с weekday-only до calendar-day запросов после обнаружения воскресных торгов 2020-01-05. Эта upstream completeness проблема учтена root до seal финального пакета.

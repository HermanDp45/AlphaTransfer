# AlphaTransfer: персонализация и сценарная синтетика

Воспроизводимое исследование поверх **неизменённых** OOT прогнозов `hgb_plus_cnyrub_basis`. Его результат — оценка свойств клиентских гейтов на синтетических расписаниях при реальных исторических официальных курсах. Это не причинная оценка uplift, не проверка поведения банка и не новый FX backtest.

## Запуск

Из `AlphaTransfer` с Python 3.11+ и NumPy/Pandas:

```bash
OPENBLAS_NUM_THREADS=1 OMP_NUM_THREADS=1 python research_v3/behavior/simulate.py
python research_v3/behavior/validate.py
python research_v3/behavior/build_report.py
```

В текущем окружении использован Python `/private/tmp/alphatransfer-ml.Ci5ycv/venv/bin/python`. Запуск ограничивает вычислительные библиотеки одним потоком. Сеть не нужна. Уменьшенный smoke:

```bash
python research_v3/behavior/simulate.py --users-per-segment 20 --seeds 4101 --scenarios base no_behavioral_response --output research_v3/behavior/smoke
```

`--output` определяет каталог результатов. Основной код и `final_solution` не изменяются.

## Семантика политик

`market_only` применяет сохранённые corridor candidates своему коридору клиента и максимум два контакта за любые семь календарных дней. У клиента один коридор; портфель из пяти направлений не выдаётся за одного пользователя. `frequency_gate` разрешает те же сигналы около ожидаемой фазы перевода, оценённой по синтетической истории до периода. `user_aware` добавляет наблюдаемый noisy intent/доступный баланс и suppression в первые три дня после совершённого перевода. История, intent и баланс — наблюдаемые inputs; скрытая будущая дата/готовность используется только для моделирования response и оценки.

`matched_random_market` получает **ровно столько же контактов у каждого клиента**, сколько `user_aware`, случайно отбирая их из исходных market candidates. `matched_calendar` получает тот же бюджет, равномерно распределяя контакты по доступным датам без market score. У обеих политик дата отбора не использует будущий курс. Quota получена из уже выполненного `user_aware` replay, поэтому это **ретроспективный budget-matched descriptive benchmark**, а не online policy или валидный causal estimand. Для пилота бюджет задаётся ex ante. `weekly_fixed` отправляет в первую доступную дату каждой календарной недели без FX score; фактический бюджет показан отдельно и не обязан совпадать.

Переводы не создаются и не исчезают. Каждый исходный перевод выполняется в исходную дату, если раньше не среагировал на push. Срочные переводы нельзя сдвинуть. У каждого события одна сумма и один transfer-id. Нет отсрочки после дедлайна или исполнения до готовности денег. Будущие события за границей периода не разрешено подтягивать внутрь него. Все клиенты остаются в denominator; нулевые контакты и нулевые gains сохраняются.

## Ограничения переноса

2023–2025 — ретроспективные OOT окна исходной модели; 2026 уже просматривался и остаётся diagnostic. Используется конвенция effective-date/publication proxy исходного решения и официальный курс, **не исторические исполнимые котировки банка**. Результат нельзя называть сбережением клиента или net contribution margin. `net_scenario_value` вычитает условные расходы из клиентской timing value; это условный joint-value proxy, не банковская прибыль. Во всех сценариях прирост объёма/числа переводов равен нулю по конструкции, но это не оценка реального эффекта равного нулю.
